# アーキテクチャ決定記録: 匿名いいね数の表示・不正対策

## ステータス

**採用: 10分キャッシュ + 最小限のbest-effort重複抑止**（2026-07-14簡略化）

## コンテキスト

いいね数は参考値であり、厳密な一人一票やリアルタイム表示を要件としない。個人開発の閲覧主体サイトとして、不正対策がサイト本体や復旧運用より複雑にならないことを優先する。

## 表示とキャッシュ

- 名言詳細・一覧のSSR HTMLへ`like_count`を含め、edge TTLを10分とする。
- 毎PVのいいね件数GET APIと、いいねごとのキャッシュパージは作らない。
- `POST /api/likes/{quote_id}`は`private, no-store`かつCloudflare Bypassとし、成功時は押した本人のDOMだけ最新件数へ更新する。
- TTL内の再読込で一時的に古い件数へ戻ることを許容する。
- `client_uuid`はlocalStorageで管理し、公開HTMLの利用者識別Cookieは作らない。

## 重複抑止とレート制限

- `(quote_id, client_uuid)`をDBの一意制約とし、同じ識別子からの再送は件数を増やさない冪等な成功とする。
- `client_uuid`はUUID形式と最大長を検証する。これは変更可能なbest-effort識別子であり、本人認証やフィンガープリントとして扱わない。
- Cloudflare側、またはアプリ側の単純な送信元IP単位の短時間レート制限を1つ設ける。初期値は10回/10秒程度とし、通常利用を誤制限する場合は緩和する。
- アプリ側でIP hashをDBへ保存しない。HMAC鍵、鍵世代、定期ローテーション、長時間bucket、複合キーLRUは導入しない。
- `Origin`、Content-Type、Fetch Metadataを検証し、不正形式はDB処理前に拒否する。
- レート超過は`Retry-After`付き429、解消できないSQLite競合は503とする。

送信元IPを信頼する場合は、ADR 013どおりCloudflare Tunnelを唯一の公開HTTP経路とし、単一で妥当な`CF-Connecting-IP`だけを使用する。IPは通常ログへ残さない。

## 不正への対応

初期リリースではTurnstile、端末フィンガープリント、専用レート制限基盤、不正検知用日次集計を導入しない。明確なbot被害やDB負荷が実測された場合に、次の順で検討する。

1. 単純なレート制限値の調整
2. Cloudflare managed challengeまたはTurnstile
3. 必要な期間だけの追加集計

不正な票を完全には防げないことを仕様として受容する。重大な水増しが起きた場合は、管理者が対象のいいねを手動で取り消せるようにする。

## Privacy Policy

`client_uuid`をlocalStorageへ保存すること、匿名いいねの重複抑止に使うこと、サイトデータの削除で端末側の値を消せることを記載する。生IPまたはIP hashをアプリDBへ保存する旨の記載は不要である。

## 検証

- 初回POST、同一`client_uuid`の再送、別`client_uuid`、存在しない名言を確認する。
- 不正なUUID、Origin、Content-Type、Fetch Metadataを拒否する。
- レート超過時の429と通常利用への影響を確認する。
- edge TTL内の古い表示と、POST直後の本人向け表示更新を確認する。

## 再検討条件

- botによる水増しや可用性影響が継続的に観測される
- いいね数をランキングや金銭的価値のある判定に利用する
- 複数Machine化によりアプリ内制限が実効性を失う
