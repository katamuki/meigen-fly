# アーキテクチャ決定記録: SQLite移管時の日本語検索方式

## ステータス

**確定: 初期リリースは単純な部分一致検索を採用する**（2026-07-14改訂）

## コンテキスト

移管元はPostgreSQL + PGroongaを使用しているが、移管先はFly.io上のSQLiteである。対象は名言約2,100件、著者約890件、合計約3,000行と小規模で、検索は読み取り中心である。

検証では`LIKE '%語%'`による全件走査でも十分高速であり、1文字・2文字の日本語も追加のトークナイザなしで検索できる。初期段階でFTS5用bigram生成、派生テーブル、同期処理、専用migrationを持つ便益は小さい。

## 決定

- 初期リリースは、名言本文、著者名、必要な補助列に対する`LIKE`部分一致を使用する。
- 入力はUnicode文字列として扱い、前後空白の除去、連続空白の正規化、最大長をアプリ側で適用する。
- SQLパラメータをbindし、利用者入力をSQL文字列へ連結しない。
- `%`、`_`、escape文字は検索構文として公開せず、`LIKE ... ESCAPE`を使ってリテラル文字として検索する。
- 結果件数には上限を設け、既存の本文一致優先など必要最小限の順位付けだけを`CASE`等で表現する。
- FTS5、bigram列、bigram生成スクリプト、形態素解析辞書は初期実装へ含めない。
- 著者検索も同じ方式を使う。

## 検証

- 1文字、2文字、複数文字、空白を含む語、日本語と英語について期待する結果を確認する。
- `%`、`_`、escape文字を含む入力がワイルドカードにならず、リテラル文字として扱われることを確認する。
- SQL injectionに相当する入力がbind parameterとして扱われることを確認する。
- 本番相当データで応答時間を計測する。通常の検索が継続的に許容範囲を超えた場合だけ再設計する。

## 再検討条件

次のいずれかが実測された場合、FTS5 + bigram、形態素解析、または外部検索基盤を比較する。

- データが数万件規模へ増え、部分一致検索が継続的なボトルネックになる
- 単純な順位付けでは検索品質に明確な問題がある
- AND/OR検索や高度な関連度ランキングがプロダクト要件になる

## 採用しなかった初期案

- **FTS5 + アプリ側bigram**: 実現可能だが、現在のデータ量では派生データと同期処理の保守コストが便益を上回る。
- **C製カスタムトークナイザ、形態素解析**: ビルド、辞書、配布の負担が初期規模に見合わない。
- **PostgreSQL + PGroonga継続**: 検索品質は高いが、SQLiteへ移して運用を簡素化する目的に反する。
