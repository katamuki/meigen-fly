# アーキテクチャ決定記録: OG画像生成方式（D5）

## ステータス

**確定: Pillowによるオンデマンド生成 + Cloudflareキャッシュを採用**（2026-07-19決定）

## コンテキスト

名言個別ページと著者詳細ページには、内容に対応した1200×630のOG画像が必要である。デザインはD8で確定したLight固定の「和紙×墨×藍」とし、サイトのLight/Darkテーマから切り離す。データ規模は名言1,831件、著者774件で、管理更新は低頻度である。

生成方式として、Pillowによる画像描画、ChromiumによるHTML画像化、全件事前生成を比較した。既存の [`proposal-b/og/og.html`](../design/proposal-b/og/og.html) は視覚仕様として完成しているが、背景、罫線、文字、ブランド表示からなる単純な構成であり、ブラウザエンジンを本番コンテナへ持ち込まなくても再現できる。

## 決定

### 生成方式とタイミング

- PythonのPillowで、OG URLへの**キャッシュミス時にオンデマンド生成**する。デプロイ時・データ移行時・定期ジョブでの全件事前生成は行わない。
- 初回アクセスではFastAPIがSQLiteから対象データを読み、PNGを生成して返す。Cloudflareにキャッシュされている間はオリジンで再生成しない。
- 管理画面で対象を更新した後は、ADR 014に従って既知のOG URLをパージする。次のアクセスが新しい画像を生成する。
- アプリ内の永続画像キャッシュ、SQLite BLOB、Fly Volume上の生成済みファイル、専用生成workerは作らない。

### URLと応答

- 名言: `GET /quotes/{slug または q{id}}/og.png`
- 著者: `GET /authors/{slug}/og.png`
- 正常時は1200×630の`image/png`を返し、`Cache-Control: public, s-maxage=2592000, max-age=86400`（エッジ30日、ブラウザ1日）を付ける。Cloudflare Cache Rulesで画像をキャッシュ対象にする。
- 名言OGの識別子は詳細ページのcanonicalと同じものを使う。クエリパラメータによるデザイン差分やキャッシュ回避機能は設けない。
- 対象が存在しない、または非公開の場合は404かつ`private, no-store`とする。描画処理だけが失敗した場合は共通の静的OG画像を`image/png`・`private, no-store`で返し、失敗をログへ残す。誤ったフォールバック画像を30日キャッシュさせない。

### デザインと表示内容

- 名言・著者ともLight固定の「和紙×墨×藍」で描画し、D8の色、余白、罫線、落款風ブランドを踏襲する。HTML/CSSファイルはPillow実装の視覚仕様とプレビューに使い、本番の画像生成には使わない。
- 名言本文はADR 009の共通resolverで主表示言語とfallbackを解決し、前後の空白を除去して連続する改行・空白を1つの空白へ正規化する。
- 名言OGは本文、著者名、ブランドを表示する。著者OGは著者名、固定補助文「名言・格言」、ブランドを表示し、関連データを増やして複雑なレイアウトにしない。
- フッターの著者名は、落款風ブランドとの間に32pxを空ける位置まで実測幅で`…`付きに切り詰める。表示幅の大きい実在の著者名がブランドへ重ならないようにするため（2026-09-10、フェーズ3-Eの実装時に追記）。

### 文字量と80字超の扱い

- 文字量は正規化後の表示幅単位で判定する。Python標準の`unicodedata.east_asian_width()`が`W`・`F`・`A`の文字を1、それ以外を0.5として合計する。これにより日本語はおおむね1字、英数字はおおむね半字として同じ閾値を使える。
- 表示幅20以下を`short`、20超40以下を`medium`、40超80以下を`long`とする。デザイン素材の`og--short` / `og--medium` / `og--long`はこの3段階の視覚仕様を表す。
- 80を超える場合は、末尾の`…`を含め表示幅80以内になる位置で切り詰め、`long`で描画する。`og--xlong`や、SNSタイムラインで読みにくくなる小さな文字段階は追加しない。
- 改行位置はPillowで実際のグリフ幅を測って決める。行頭禁則文字が行頭に残る場合は直前の行へ戻す、または直前の文字とまとめて送る最小限の禁則処理を行う。
- 実装では「直前の文字とまとめて送る」方式を採る。直前の行へ戻す方式は、その行に余裕がないと本文が右端からはみ出すため（2026-09-12、フェーズ3-Eのレビュー修正で追記）。

### フォント

- 本番DockerイメージにDebianの`fonts-noto-cjk`と`fontconfig`パッケージを導入し、Pillowから`Noto Serif CJK JP`をローカルファイルとして使用する。OG生成時に外部URLからフォントを取得せず、サイト本体のWebフォントとしても配信しない。
- Dockerビルド時に`fc-match`で日本語明朝フォントを解決できることを検査し、見つからなければビルドを失敗させる。本番で別フォントへ黙ってfallbackさせない。
- 実装時はPillowを`pyproject.toml` / `uv.lock`で固定する。Chromium、Playwright、WeasyPrint等の画像生成依存は追加しない。

## 理由

- 低頻度更新と30日エッジキャッシュにより、生成回数はキャッシュミス時だけでよく、全件ファイル管理は不要である。
- Pillowなら既存のPythonプロセス内で完結し、Chromium本体、ブラウザ起動、追加のプロセス管理・メモリを持ち込まずに済む。
- OG画像は単純な固定キャンバスで、HTML/CSSの完全なレイアウト機能を必要としない。実測幅で折り返す方が、固定されたフォントと出力サイズに対して挙動を検証しやすい。
- 80字超をさらに縮小すると、タイムライン上の可読性が下がる。OG画像は全文表示ではなくリンク先への要約表示と位置付け、省略を許容する。

## 検証

- 名言の表示幅20・21・40・41・80・81、および全角・半角混在と英文で、段階選択と省略位置を単体テストする。
- ADR 009の`ja` / `en`選択と片側欠損fallbackがHTML・metadata・OGで一致することを確認する。
- 実データの短文、中文、長文、80超、長い著者名を1200×630とタイムライン縮小で確認し、本文、著者名、ブランドが重ならないことを確認する。
- 正常時のPNG寸法・Content-Type・Cache-Control、404、描画失敗時のno-storeフォールバックを確認する。
- Cloudflareで2回目がHITになること、管理更新後のURLパージと次回アクセスで画像が更新されることを確認する。
- 本番DockerイメージでNoto Serif CJK JPが解決され、ローカル検証画像と同じ改行になることを確認する。

## 再検討条件

- OG画像のデザインが複雑化し、PillowではHTML/CSSとの二重管理が実害になる場合。
- 生成時間またはメモリ使用量が本番で問題になり、Cloudflareキャッシュでも吸収できない場合。
- 画像種類や更新件数が大幅に増え、事前生成の方が運用を単純化できる場合。
- SNS側の仕様変更により、異なる寸法・形式・複数バリエーションが必要になった場合。

## 採用しなかった案

- **ChromiumによるHTML画像化**: デザイン素材を直接使える一方、ブラウザ本体、起動時間、Dockerサイズ、メモリ、プロセス管理の負担が固定キャンバス1種類には大きい。
- **全件事前生成**: 初回応答は速いが、デプロイ・移行・更新時の生成対象管理、生成済みファイルの保存・削除・同期が増える。現在の件数とCloudflareキャッシュでは不要。
- **アプリ内永続キャッシュ**: Cloudflareと二重の失効管理になる。単一MachineでもVolume上のファイル整合や掃除が必要になるため採用しない。
