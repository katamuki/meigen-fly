# アーキテクチャ決定記録: Cloudflareキャッシュの更新反映

## ステータス

**確定: 同期パージ + TTLによる自然失効を採用**（2026-07-14簡略化）

## コンテキスト

公開HTMLはCloudflareでキャッシュするが、管理画面の更新頻度は低い。個人運営では数秒以内の確実な反映より、実装と障害対応を単純に保つことを優先する。通常ページは10分から1時間程度で自然失効する。

## 決定

- 管理画面の更新transactionが成功した後、関連する少数のURLまたは集合タグをCloudflare APIへ同期送信する。
- パージ要求には短いtimeoutを設定する。成功すれば更新完了として表示し、失敗した場合は更新自体を取り消さず、管理者へ「キャッシュ反映はTTL待ち」と表示してログへ残す。
- 通常処理では自動retry、SQLite outbox、lease、非同期flusher、常駐worker、専用queueを作らない。
- 個別名言・著者等の詳細ページと既知のOG画像はURLパージを基本とする。
- 追加・削除・並び順変更では、対象となる一覧の集合タグ、または列挙しやすい一覧URLをパージする。
- `sitemap.xml`はURLパージする。
- ランキングは再計算成功後に`/ranking`とトップページをパージする。
- いいねごとのパージは行わず、ADR 006どおり10分TTLで更新する。
- 大量更新時は細かな個別パージをせず、集合タグ、必要に応じた手動Purge Everything、またはTTLへ委任する。

## 最小のパージ対応表

| 更新 | パージ対象 |
|---|---|
| 名言の追加・編集・削除 | 旧新の詳細URL、名言一覧、トップ、`sitemap.xml`、既知のOG URL |
| 著者・カテゴリ等の追加・編集・削除 | 旧新の詳細URL、対応する一覧、影響が明らかな関連ページ、`sitemap.xml` |
| 関連付け変更 | 対象名言または著者の詳細、関係する一覧 |
| ランキング再計算 | 成功後にランキングとトップ |
| いいね | パージしない |

初期実装では列単位の依存グラフや、描画した全entityの個体タグを作らない。多少広めに一覧をパージすることを許容する。

## 失敗時の扱い

- timeout、429、5xxではログへ状態を残し、通常ページはTTLによる自然失効を待つ。
- 管理者は必要なら管理CLIまたはCloudflare Dashboardから同じURL、集合タグ、Purge Everythingを手動実行できる。
- 秘密情報の誤公開などTTLを待てない場合は手動パージし、元の資格情報等も必要に応じて失効する。キャッシュパージだけで既に取得された情報を回収できるとはみなさない。

## 検証

- 代表的なCRUDで想定URLまたは集合タグが送られる。
- Cloudflare API成功後に新しい内容が取得できる。
- timeout、429、5xxでもDB更新は保持され、管理者への表示とログが残る。
- パージしない場合も設定したTTL以内に内容が更新される。
- 大量移行では不要なAPI要求を送らない。

## 再検討条件

次が実測された場合にだけ、再送や永続outboxを検討する。

- 管理更新が頻繁になり、同期パージが操作性へ影響する
- パージ失敗が反復し、TTL待ちが運用上の問題になる
- 複数管理者・複数Machineから大量更新する
- 法的または契約上、短時間の反映保証が必要になる

## 採用しなかった初期案

- **SQLite outbox + 非同期flusher**: 低頻度の管理更新に対し、状態遷移・再送・shutdown処理・並行性テストの負担が大きい。
- **更新ごとの詳細な個体タグ依存グラフ**: 正確だがroute追加時の保守負担が大きい。
- **外部queue**: 現在の更新量では不要。
