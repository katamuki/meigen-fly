現行のPostgreSQL/SupabaseからSQLiteへ移行するために、次を行う。

## 重要な設計方針

現行のmeigensyuのDB構成を、そのまま正しい設計として扱わない。

現行DBは、長期間の機能追加・仕様変更・migrationの積み重ねにより、次のような歪みを含んでいる可能性がある。

- 現在は不要なテーブルやカラム
- 役割が重複するテーブル、ビュー、RPC
- PostgreSQL／Supabase固有の都合で追加された構造
- 過去の仕様に由来する名前や制約
- 不要になった集計テーブルやマテリアライズドビュー
- アプリ側とDB側に不自然に分散した処理
- 本来DB制約で保証できるが、アプリだけで検証している項目
- 現在の規模に対して過剰に複雑な制約や集計処理
- migration上は存在するが、現行アプリでは使われていないオブジェクト
- 移行や過去データ修正のためだけに追加された一時的な構造

守る対象は、原則として次のものとする。

- 現在必要なコンテンツデータ
- 公開ページと管理画面に必要な機能
- URL互換性に必要なID、qid、slug、関連情報
- 名言、著者、カテゴリ、登場人物、出典、職業、国などの正しい関連
- いいね、ランキング、検索、集計などの必要な振る舞い
- 移行後も保持すべき履歴・集計元データ
- 現在公開中のコンテンツの意味と表示内容
- 非公開、下書き、編集中を含む、本番DB上で管理対象になっているコンテンツデータ

公開・非公開を問わず、本番DBに存在するコンテンツデータは原則として棚卸し対象とする。削除候補にする場合は、件数、利用箇所、データの意味を確認し、ユーザー判断なしに移行不要と確定しない。

現行のテーブル構成、ビュー、RPC、カラム名、内部的な実装方法そのものは、必ずしも維持対象ではない。

必要であれば、現行テーブルの統合、分割、改名、カラム削除、関連方法の変更を提案してよい。ただし、変更理由と、保持されるデータ・振る舞いを明記する。

## 新DB設計の判断基準

meigen-flyの要件、データ規模、FastAPI + SQLAlchemy Core + SQLiteという構成に合わせ、次の基準で検討する。

1. 必要なデータを欠損なく保持できる。
2. 公開ページと管理画面のクエリを単純に実装できる。
3. 外部キー、UNIQUE、CHECKなどで基本的な整合性を保証できる。
4. PostgreSQL／Supabase固有機能への依存をなくす。
5. 原本データと派生データを明確に区別する。
6. 不要なキャッシュテーブル、ビュー、RPCを持ち込まない。
7. 主要コンテンツは名言約2,100件・著者約890件の小規模サイトとして単純な構成にする。ただし、中間テーブル、いいね、ランキング履歴などを含むDB全体の行数は未確認であり、本番DBの確認事項として過小評価しない。
8. 仮想的な将来要件のための構造を追加しない。
9. 用途が理解しやすい名前と関連にする。
10. データ移行、検証、バックアップ、復旧が容易である。
11. SQLiteの制約と特性に自然に合う。
12. 現行URLとコンテンツの互換性を維持できる。

### 情報源の優先順位と確度

情報が食い違う場合は、原則として次の優先順位で扱う。

1. 本番schema dump: 実在するDB構造の最終的な正本
2. 現行アプリコード: 現在使用している機能とクエリの根拠
3. 生成済みDB型: 生成時点のDB構造

5. 文書: 設計意図と運用経緯の参考情報

今回は本番DBへ接続せずschema dumpも取得しないため、各重要な結論へ次のいずれかの確度を付ける。

- **確認済み**: 複数のリポジトリ内情報が一致している
- **リポジトリから推定**: 根拠はあるが、本番の実在状態を未確認
- **本番確認待ち**: schema driftや実データを確認しないと確定できない

本番schema dumpを後続作業で取得した場合は、それを実在構造の正本として差異を再評価する。

## 現行DBオブジェクトの分類

分類の重複を避けるため、各オブジェクトについて「構造の扱い」と「データの扱い」を分けて記録する。

### 構造の扱い

1. 維持: SQLiteでも概ね同じ責務と構造を使う
2. 再編: 統合、分割、改名、制約変更などを行う
3. 処理へ置換: リアルタイムSQLまたはPython処理へ置き換える
4. 廃止: PostgreSQL／Supabase固有、未使用、重複などのため持ち込まない
5. 本番確認待ち: 本番スキーマや実データを確認しないと判断できない

### データの扱い

1. そのまま移行: 原本データを同等の値で移す
2. 変換して移行: 型、形式、関連先などを変換して移す
3. 再計算: 派生データのため移行後に作り直す
4. 移行しない: 不要、一時データ、廃止対象などのため移さない
5. 本番確認待ち: 件数、内容、利用実態を確認しないと判断できない

それぞれの判断理由を簡潔に記載する。複数のデータ種別を含むオブジェクトは、必要に応じて行やデータ種別を分けて記載する。
